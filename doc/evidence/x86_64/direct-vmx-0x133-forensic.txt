    <direct-vmx-evidence-workdir>/windows-hyperv.qcow2

The verifier starts exactly this image server:

  qemu-nbd -r -f qcow2 -k <temporary-unix-socket> <top-image>

It negotiates the default NBD export and sends only NBD_CMD_READ requests.
It does not expose a writable export, mount a filesystem, create an extracted
dump file, or connect a kernel NBD device. The socket lives in a Python
TemporaryDirectory. The client socket is closed and qemu-nbd is terminated in
a finally block.

Chronology cross-check
----------------------

  The MEMORY.DMP SystemTime FILETIME mechanically decodes to
  2026-08-30 12:41:53.719276 UTC. QEMU was configured with
  `-rtc base=localtime`, while the serial artifact mtimes below are host JST;
  therefore this is a matching guest/host wall-clock sequence, not a claim
  that the two timestamp domains have the same UTC offset.
  The subsequent UEFI epoch is visible in the existing serial artifacts:

    monitor-hyperv-desktop-serial.log mtime:
      2026-08-30 12:42:31.631021047 +0900
    monitor-hyperv-serial.log mtime:
      2026-08-30 12:42:32.459035801 +0900

  monitor-hyperv-serial.log contains a new BdsDxe Boot0002 sequence and a new
  thin-hv UEFI/runtime-monitor epoch after the preceding direct nested-VMX
  activity. This is distinct from the direct KVM control's earlier 09:55

Forensic conclusion and limit
-----------------------------

The current qcow2 chain independently confirms the documented MEMORY.DMP hash,
0x133 code and all four parameters, SystemTime, and uptime. It also independently
confirms the documented WER minidump hash, LogonUI.exe process identity,
0xc0000005 exception, and Windows.UI.Logon.dll containing module.

Parameter 1 equal to 1 is consistent with a cumulative watchdog timeout at
DISPATCH_LEVEL or above. The header and WER minidump do not identify a specific
driver as the cause, and this transcript makes no such attribution.
